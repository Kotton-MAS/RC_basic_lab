## 2. 【B】記事05 —— UCR を使っていない

`results/05_anomaly_detection/meta.json`:

```
dataset: { source: "mgab", series: ["1","2","3"], max_length: 60000,
           train_ratio: 0.25, calibration_ratio: 0.15 }
```

`anomaly.csv` は 90 行すべて `dataset=mgab`(3系列 × 5レプリケート × 6系統)。
`datasets/ucr.py` に取得コードはあるが、**記事の数値は UCR を1点も含まない**。

したがって以下は実測の裏付けが無い:

- 冒頭「UCR Anomaly Archive と MGAB」
- §6 限界「UCR は系列ごとに性質が違って、単一の大域設定では回りません。系列ごとに前処理を切り替えていて…」
- §5 意外だった点の候補 (b)「UCR が単一の大域設定では回らず、系列ごとに前処理が要ったこと」

さらに **MGAB は Mackey-Glass に人工的な異常区間を挿入した合成ベンチマーク**である。
タイトル「実データで異常検知をやってみる」および冒頭
「#1〜#4 はすべて合成データだったので、ここで初めて外部の実データを使います」は、
厳密には成立しない。正しくは「**外部の公開ベンチマーク**を使う」。

**選択肢は二つ**:
1. UCR を実際に回して、記事の記述どおりの実験にする(`make data-05` + `source: ucr`。ライセンス未指定なので本体は同梱しない方針は維持)
2. 記事を MGAB 単独に合わせて書き直す(タイトル・導入・限界節)。合成 vs 実データの軸は「限界と次」で正直に書く

「否定的結果も正直に書く」を差別化に置いている連載なので、**2 を選んでも記事の価値は落ちない**。
むしろ「実データに行きたかったが MGAB で止めた。理由はライセンスと予算」と書くほうが連載の芯に合う。

### 数え方の不整合(軽微)

冒頭「対照を6本置きました。結果、**5本**が一様乱数と区別できませんでした」。

## 3. 【C】記事02 §3.4 —— washout は「効く」ではなく「効かない」

`results/02_esp_and_dynamics/washout_sensitivity.csv`(補償あり、washout = 0/50/100/200/400/800):

| 課題 × 手法 | NRMSE の max/min |
|---|---|
| MG × 線形 | 1.000 |
| MG × 遅延線 | 1.004 |
| MG × ESN | 1.008 |
| パリティ × 線形 | 1.000 |
| パリティ × 遅延線 | 1.001 |
| パリティ × ESN | 1.005 |

`washout_sensitivity_unpadded.csv` でも最大 1.012。**6組すべてでレプリケート間のばらつきの内側**。

そして `docs/series/要件_rc-basics-02.md` の「決定済み事項 5」に、すでにこう書いてある:

> 当初の予測「遅延パリティは washout に反応しない対照になる」は**データで支持されなかった**:
> 補償後は6組すべてで変動幅がレプリケート間のばらつきの内側で、**どちらの課題も反応しない**。
> 補償を外すと MG × ESN の NRMSE は washout に対して完全に単調増加(比 1.0115)するが、**それは訓練データ量の効果だった**。

一方、記事02 の本文は:

- 結論テーブル4行目「washout の長さは結論を変えるか → TODO: 実測値を入れる」(空欄のまま)
- §3.4「TODO: 論文間で washout がバラバラで、**しかも結果に効く**という話。比較可能性の問題として書く」

**書くべき向きが逆**。正しい筋は次のとおりで、しかもこちらの方が記事として強い:

> washout は論文間でバラバラだが、**訓練データ量の交絡を除くと結果に効かなかった**。
> 効いて見えるのは washout そのものではなく、washout を伸ばした分だけ訓練データが減っていたから。
> つまり「washout が結果に効く」という直感は、交絡を除くと消える。

結論テーブル4行目もこれで埋まる(❌ 変えない。比 1.012 以内)。

## 4. 【D】記事02 §4 —— しきい値では境界が動かない

`esp_threshold_sensitivity.csv`(abs_tol = 1e-4 / 1e-6 / 1e-8 × window = 100 / 200 / 400 の9条件):

- 全条件で `n_sigma_shifted = 0`、`max_abs_shift = 0.0`
- `critical_rho` は σ_u = 0 → 1.0、0.05 → 1.1、0.1 → 1.1、0.2 → 1.3、0.5 → 1.5、1.0 → 1.7、2.0 → 境界なし(全域で成立)

§4 の候補 (b)「判定しきい値の選び方で成立域の境界が**どれくらい動くか**。(b) が一番書きごたえがありそう」は、
実測では **しきい値を4桁動かしても境界は1格子も動かない**。
書くならロバストネスの話(「結論はしきい値の選び方に依存しない」)であって、感度の話ではない。

**あわせて**: §3.2 は記事の主図の節なのに、本文に数値が1つも無い。
上の `critical_rho` の数列(1.0 → 1.1 → 1.3 → 1.5 → 1.7 → 境界なし)を本文か小表に入れるだけで、
「境界が動く」が一気に具体的になる。ここは今すぐ埋められる。

## 5. 【E】記事02 §3.3 —— 「約1.4倍で平行」は τ の定義に依存する

`esp_diagnostics.csv`(2B_timescale、レプリケート3本平均、理論値 = −1/log(1−a)):

| リーク率 a | τ_1e / 理論 | τ_integrated / 理論 |
|---|---|---|
| 0.1 | 1.411 | 1.579 |
| 0.2 | 1.405 | 1.550 |
| 0.3 | 1.324 | 1.585 |
| 0.5 | 1.338 | 1.722 |
| 0.7 | 1.338 | 1.938 |

- **τ_1e(1/e 到達)** なら 1.32〜1.41 で、おおむね「約1.4倍で平行」と言える(ただし 1.41 → 1.33 とわずかに減る)

§3.3 の TODO「1.4倍のずれが何に由来するか(測り方の定義差だと思われる)」は、

### 7.6 「負け」の反復をどこで受け止めるか

連載の弧(01 負け → 03 負け → 04 勝ち → 05 勝ち)は非常に良い。ただし:

- 01 は「MG では遅延線に負けた」と同時に「**非線形課題では ESN だけが解けた**」という勝ちも持っている
- 現状の 01 は §3.1 の見出しが「片方の課題では遅延線に負ける」で、負け側から入っている

1本目から負けで入ると読者が離脱しやすい。
01 は「**対照を置くと何が見えるか**」を主題にして、勝ち負け両方を同格に置く。
「負け続ける」という緊張は 03 から始めたほうが、04 の解放が効く。

### 7.7 総括と番外編の置き場

未決が2つ残っている:

- 05 素案メモ「連載の総括をこの記事に置くか、別記事にするか」
- 04 素案メモ「乱数バグの経緯をどこまで書くか。#4 本文に置くか、連載の振り返り記事に回すか」

構成案の方針は「**5本で必ず切り上げて本編に入る**」。これは守るべき。
一方で 05 は目安 8,000〜10,000字 + 図5枚 + 総括、と最も重い。

推奨: **総括は 05 の末尾に短く置く**(「5本中3本で遅延線に負けた」という一覧表1つで足りる)。
乱数バグとエージェント運用の話は **本編開始後の番外編**へ回す
(`docs/process/agent-operations-retrospective.md` と `docs/process/agent-system-review-from-artifacts.md` が既にあり、素材は揃っている)。
これなら「5本で切り上げる」を守りつつ、04 の本文が軽くなる。

ただし 04 §4 の乱数バグの話は**記事の芯に近い**(「単調に減るという解釈そのものがバグの産物だった」)ので、
経緯の詳細は番外編へ回しつつ、**結論と教訓の2段落は 04 に残す**。
