# エージェント運用の指摘 — 成果物側から見た修正点

*作成: 2026-08-20 / 対象: `rc-basics-lab` のサイクル 01〜04 と、それを回した運用の仕組み*
*先に読むもの: `docs/agent-operations-retrospective.md`*

---

## この文書の位置づけ

`docs/agent-operations-retrospective.md`（以下「振り返り」）は**過程の記録**から書かれている。素材は `~/.claude/incidents.jsonl`（84 件）、`.claude/decisions.yaml`（53 件）、各サイクルの findings（199 件）である。

本稿は**出来上がった成果物そのもの**を外部から読んで気づいた点を扱う。素材は `src/`、`tests/`、`results/`、`CLAUDE.md`、`.claude/settings.json`、`git log` である。

両者は重複しない。

| | 振り返り | 本稿 |
|---|---|---|
| 素材 | 過程の記録 | 成果物の現物 |
| 扱う対象 | ガードが破れた回数 | **ガードが全部通ったのに残っているもの** |
| 見つかる問題 | 再発するもの | 一度も検出されなかったもの |

したがって本稿の指摘は振り返りの提言 1〜6 と競合しない。ただし**指摘 4 は提言 1 の前提を壊す**ので、提言 1 に着手する前にそこだけ先に読むこと。

---

## 0. 要約

1. **評価軸に「読み手」が一度も入っていない。** システムが持つ品質の軸は正しさだけで揃っており、8 サイクルで単調増加している。削除・統合を要求する仕組みがゼロ
2. **`CLAUDE.md` がテンプレートのまま 8 サイクル回っている。** プレースホルダが未置換、無関係なセクションが約 40 行、学習メモが空。「プロンプト層は効かない」という結論は、プロンプト層を一度も本気で書いていないことの結果でもある
3. **無検査の散文は `decisions.yaml` の rationale だけではない。** src の docstring 約 6,000 行が同じ性質を持つ
4. **フックが動く処理系がプロジェクトのコードを解析できない。** 提言 1 を実装した瞬間に破綻する
5. **773 件の同一メッセージ wip コミットで git 履歴が機能していない。** 振り返り 2.1 節の検出経路がサイクル数に比例して悪化する
6. **サイクル終了時の後始末が定義されていない。** 589MB の worktree が gitignore の外に残っている

## 1. 評価軸に「読み手」が一度も入っていない（最重要）

### 観測

| 指標 | 値 | 8 サイクルでの方向 |
|---|---|---|
| テスト数 | 439 → 964 | 単調増加 |
| 決定（`decisions.yaml`） | 53 件 | 単調増加 |
| `src/` | 18,660 行（実コード 9,900 / docstring 32%） | 単調増加 |
| 最大モジュール | `freerun.py` 1,620 行 | 単調増加 |
| 削除・統合を要求した findings | **0 件** | — |

### 診断

このシステムが持つ品質の軸は「正しさ」だけで揃っている。guard_test、evidence 検証、成果物のバイト不変検査、変異注入 — どれも**壊れていないこと**を測る。**読めるか・伝わるか・使えるか**を測る軸が 1 本も無い。

結果として、どのガードにも触れないまま以下が残った。

- 実験 4 本ぶんの同じ骨格が 4 回書かれている。`_new_figure` / `_save` が 4 コピー、`write_*_csv` が 11 本、`# type: ignore` が 16 箇所（詳細は `docs/リファクタリング方針.md`）
- 図に文献比較がほとんど無い。成果物は「正しく生成されている」ので、どのテストも赤くならない（詳細は `docs/図の設計方針_RC基礎編.md`）
- docstring が 32% を占め、その中身が rationale の 3 重複になっている（指摘 3）

いずれも**正しく、かつ読めない**。この系のガードはそれを検出できる設計になっていない。

### 対応（層: 手続き層）

サイクルに reviewer を 1 体足す。軸は**「削れるか」**。

- 出力は既存の findings と同形式にする。ただし**すべての finding が削除・統合・移動の提案**であること
- 受け入れ条件は「振る舞い不変・成果物バイト不変」
- **新しい機械層を作らずに済む。** 既にある最強のガード（バイト不変検査）を、初めて「守る」側ではなく「攻める」側で使うことになる

振り返り 4 節は「成果物のバイト不変検査」を効いた対策として挙げているが、この道具は**変更を止める方向にしか使われていない**。ガードは「壊すな」しか言えず、「整理しろ」は言えない。整理を要求するのは手続き層の仕事である。

## 2. `CLAUDE.md` がテンプレートのまま 8 サイクル回っている

### 観測（すべて現物）

- **204 行。** テンプレート自身が掲げる「200 行以下を維持する（長いほどコンテキストを圧迫する）」を既に超えている
- 「このプロジェクトは \_\_\_\_\_ を行う Python モノレポです。」— **プレースホルダが未置換**
- 「アーキテクチャ原則」が `<!-- TODO -->` ＋「認証・認可は既存の共通基盤を使用し、独自実装しない」の 1 行のみ。numpy の数値実験リポジトリに 1 つも該当しない
- 「セキュリティ原則」約 40 行（SQLi / XSS / パラメータ化クエリ / Key Vault / 本番デプロイ / 個人情報のログ出力）— 同じく 1 つも該当しない。テンプレートは冒頭で「**該当しないセクションは丸ごと削除する**」と自分で指示している
- **「学習メモ（Claude のミスから追記）」が空**

### 診断

最後の 1 点が効いている。テンプレートが用意した唯一の学習機構が、**8 サイクル・84 incidents・199 件の findings を経て一度も使われていない**。

学習の行き先は代わりにこう散っている。

| 行き先 | 分量 | 次サイクルの Claude が最初に読むか |
|---|---|---|
| `docs/agent-operations-retrospective.md` | 321 行 | いいえ |
| `docs/review-findings-01〜03b.md` | 506 行 | いいえ（ID 参照時のみ） |
| `docs/plans/rc-basics-*.md` | 4,392 行 | いいえ |
| `CLAUDE.md` 学習メモ | **0 行** | はい |

さらに「コード規約」は 3 行しかない。

```
- Python 3.12+、型アノテーション必須
- `Any` 禁止（`object` か `Protocol` を使用）
- 関数は単一責任、50行超は分割を検討
```

ファイル長・モジュール分割・docstring の粒度に関する規約が**無い**。1,620 行のモジュールと 32% の docstring を止めるルールは、最初から存在しなかった。

### 振り返りの結論への補足

振り返りは「効いたのは一貫して機械層、効かなかったのは一貫してプロンプト層」と結論づけている。この結論は 84 件の実測に基づいており、正しい。

ただし**プロンプト層が一度も本気で書かれていない**という事実を併記すべきである。テンプレートの穴埋めすらしていない文書に対して「プロンプト層は効かない」と結論づけるのは早い。機械層への移行は正しい判断だが、**プロンプト層を書かない理由にはならない**。

### 対応

1. TODO を埋め、該当しないセクション（ISMS / セキュリティ / 認証認可 / 本番デプロイ）を削除する。**40 行以上減る**
2. 空いた行数で「コード規約」を実態に合わせて厚くする。最低限、モジュールの行数上限、docstring に書いてよいもの／いけないもの（指摘 3）、実験を 1 本足すときに触ってよい場所
3. **「学習メモ」を振り返りの提言の着地先にする。** 振り返りは読み物として残し、そこから `CLAUDE.md` に落ちた行だけが次サイクルに効く、という関係を明示する

## 3. 無検査の散文は `decisions.yaml` の rationale だけではない

### 観測

振り返り 2.4 節は「`.claude/decisions.yaml` の rationale だけが機械照合の外にある」とし、それを提言 1 の最優先事項に置いている。

実際には、同じ性質の無検査散文がもう一つある。**`src/` の docstring 約 6,000 行**である。

| # | 場所 | 分量 | 検査 |
|---|---|---|---|
| 1 | `.claude/decisions.yaml` の rationale | 53 件 | スキーマのみ |
| 2 | `docs/design.md` | 1,687 行 | `test_design_doc.py`（1,231 行）が機械照合 |
| 3 | `src/**/*.py` の docstring | 約 6,000 行 | **無検査** |

3 箇所に同じ rationale があると、3 箇所が独立にドリフトする。振り返り 2.5 節の 2 件（`stability.py` と `freerun.py` の docstring が実装と逆）はこのドリフトの実例であり、うち 1 件は成果物 320 行中 240 行の数値誤りにつながっている。

にもかかわらず、提言 2 はこれを「**禁止構造を宣言した docstring**」に限定してしまっている。範囲が狭い。

### 診断

`CLAUDE.md` と `decisions.yaml` は「散文で残すと後続の fixer が一貫性のために潰しても何も落ちない」を理由に `decisions.yaml` への記録を求めている。**この規律は正しい。しかし docstring 側に「書くな」が無い。** 片側だけの規律なので、rationale は decisions.yaml に**足された**が、docstring から**取り除かれなかった**。

具体例（現物）: `experiment/capacity_pipeline.py::SectionTiming` の docstring は 20 行あり、その大半が「3-C だけ意味が違う理由」と「フィールドを足す代案を採らなかった理由」である。どちらも decisions.yaml に属する内容である。

### 対応

- **プロンプト層**: `CLAUDE.md` の「コード規約」に 1 行足す — 「docstring に書くのは *何を返すか・前提・送出する例外* のみ。*なぜ / 以前は / 代案 / 実測の経緯* は `decisions.yaml` か `adr/` へ。コードには ID 参照だけ残す」
- **機械層**: docstring 内に `なぜ` `以前は` `代案` `検討したが` 等の語が現れたら落とす lint を 1 本。粗い検査だが、ドリフトの発生源を入口で塞ぐ
- 提言 2 の対象を「禁止構造を宣言した docstring」から「**実装の性質を主張するすべての docstring**」に広げる

## 4. フックが動く処理系がプロジェクトのコードを解析できない

**提言 1 に着手する前に、これを先に直すこと。**

### 観測

`.claude/settings.json` が `PYENV_VERSION: "3.10.0"` を固定している。理由も同ファイルに記録されている。

> pyenv には system と 3.10.0 しか無いため、pyenv shim 経由の python3 が「version 3.12 is not installed」で必ず失敗する。（中略）`check-decisions.sh`（decisions.yaml のスキーマ検証）と `record-incident.sh`（incidents.jsonl への記録）が**無言で死んでいた**。

これは回避策が恒久設定として残っている状態であり、副作用がある。

**このリポジトリのコードは Python 3.12 の構文を使っている。** `diagnostics/ipc.py:199` の PEP 695 型エイリアス（`type TargetSpec = ...`）は 3.10 では構文解析できない。実測（3.10.12 で `ast.parse`）で SyntaxError になることを確認した。

### 診断

現在フックがやっているのは `decisions.yaml` のスキーマ検証だけなので実害は無い。

しかし**振り返りの提言 1（rationale の数値を一次資料と機械照合する）を実装した瞬間に破綻する**。一次資料には `src/` のコードと `results/` の実測値が含まれ、それを読むには 3.12 が要る。提言 1 は最優先事項に置かれているので、この順序で踏む可能性が高い。

さらに一般化すると、これは振り返り自身が 2.1 節で見つけた形と同じ失敗である。**「無言で死ぬ」ことを検出する仕組みが無い。** 今回は `_comment_env` に人手で記録されたから分かったが、次に同じことが起きたときに気づく仕組みは追加されていない。

### 対応

1. 恒久対処（`pyenv install 3.12` + PyYAML の導入、またはキット側スクリプトのフォールバック追加）を実施し、`PYENV_VERSION` の固定を消す。**提言 1 の前に**
2. フックに「起動できたこと」を incidents に残させる。sentinel が一定サイクル現れなければ死んでいると判定できる。無言の死を検出可能にする

## 5. 履歴が git に残っていない

### 観測

| 項目 | 値 |
|---|---|
| 総コミット数 | 779 |
| うち `wip: subagent 完了時の自動コミット (1 files)` | **773**（メッセージが全件同一） |
| 粒度 | 1 ファイル（直近 10 件はいずれも 1〜39 行の変更） |
| ブランチ | `feat/rc-basics-lab`（8 サイクル分が squash もマージもされていない） |

`CLAUDE.md` は「コミット自体はキットの SubagentStop フックが自動で行う（wip コミット。**PR 前に squash する**）」と書いているが、8 サイクル経過して squash も PR も行われていない。

### 診断

`git log` / `git bisect` / `git blame` が**運用上ほぼ機能しない**。

これは振り返り 2.1 節と直結する。「変異注入のためにコードを一時的に壊した状態が wip コミットに焼き付いた」5 回は、いずれも**オーケストレータが `git log` を見て気づいた**とある。773 件の同一メッセージの中から見つけたということになる。

**この検出経路はサイクル数に比例して悪化する。** 提言 3（`block-mutations.sh` の検出範囲拡張、または `auto-commit.sh` 側での残留変異検査）が実装されるまでの間、唯一の検出手段がこれである。

### 対応

サイクル完了の定義に「そのサイクルの wip を 1〜数コミットへ squash し、意味のあるメッセージを付ける」を入れる（手続き層）。

squash が重ければ、最低限**サイクル境界にタグを打つ**だけでも `git log <tag1>..<tag2>` が使えるようになり、検出コストが一定に保たれる。

## 6. サイクル終了時の後始末が定義されていない

### 観測

- `.claude/worktrees/rc-basics-05/` にリポジトリ丸ごとのコピーが **589MB** 残っている（`__pycache__` / `.ruff_cache` / `.coverage` / `.pytest_cache` 込み）
- `git worktree list` 上は `prunable`（＝既に用済み）と表示される
- `.gitignore` は `.claude/cache/` `.claude/logs/` `.claude/tmp/` を無視するが、**`.claude/worktrees/` は入っていない**

### 診断

現在たまたま追跡されていないだけで、`git add -A` 1 回で 589MB がコミットされる。自動コミットフックが動く運用でこの状態は危うい。

### 対応

1. `.gitignore` に `.claude/worktrees/` を追加（即時、1 行）
2. サイクル完了手続きに `git worktree prune` を入れる

## 7. レビューの深さがサイクル間で揃っていない（優先度: 低）

### 観測

| サイクル | findings 件数 | 記録文書の行数 |
|---|---|---|
| 01 | 34 | 199 |
| 02 | 18 | **47** |
| 03 | **81** | 154 |
| 03b | 41 | 106 |
| 04 | 25 | — |

03 で急増し、`03b` という再サイクルが必要になっている。記録の厚みも揃っておらず、`review-findings-02.md` は「今回は充実した記述は次サイクル（T5）に譲り、ID と 1 行要約の対応表のみ」と自ら断っている。

### 診断

深さのばらつき自体は問題ではない。問題は**どの深さで回したかがサイクル間で比較できない**ことである。「03 で 81 件出た」が、実装が悪かったのか、レビューが厚かったのかを後から区別できない。

### 対応

findings 数を品質指標として読むつもりがあるなら、レビューの投入量（round 数・reviewer 種別・対象範囲・変異注入の実施有無）を 1 行のメタとして findings 記録の先頭に残す。

## 9. 構造として評価しておく点

「効いたのは機械層、効かなかったのはプロンプト層」という結論を、84 件の incidents と 13 件の空虚なガードの実測から出している点は、エージェント運用の文書として質が高い。特に以下の 2 つは、他プロジェクトにそのまま持ち出せる知見である。

- **2.6 節**: 同じ症状に見える 2 つの別の失敗（F と F-2）。「症状で対策を選ぶと外す」「再発回数は失敗の仕方で数える」
- **2.6 節末尾**: fixer が findings の *issue* には従い *fix* の提案には従わなかった記録。「レビュアーは問題の発見には強いが、再発の歴史を持っていない」「履歴は文書に書いてあるだけでは伝わらず、指示に載せる必要がある」

本稿の指摘 1〜3 は、その結論の**適用範囲**についての指摘であって、結論そのものへの反論ではない。

機械層は「壊れていないこと」を強制できるが、「読めること」は強制できない。**後者を担う層がまだ無い**、というのが本稿全体の要点である。

## B. 指摘 A-1: D-63 がプロンプト層と機械層で射程が食い違っている

## C. 指摘 A-2: docstring 規約に guard が無く、新規コードが規約前と同じ比率で書かれた

### 観測

`src/` 全体の docstring 比率は 32% → **29%**。`docs/削減候補-05.md` の自己申告（#1 は「部分完了 −135 行」）と整合する。

問題は**規約が `CLAUDE.md` に入った後に書かれたコード**である。

|---|---|---|
| `config/anomaly05.py`（05 新規） | 190 / 351 | **54%** |
| `tasks/anomaly.py`（05 新規） | 192 / 529 | 36% |

| （参考）`diagnostics/_capacity.py`（規約前） | 445 / 829 | 54% |

### 診断

**`reviewer-deletion` をサイクル完了の必須手順にする**のがこのプロジェクトの設計に合う。現状は初回 1 度きりの実行になっている。`CLAUDE.md` の「テストルール」か「Claude への作業指示」に、サイクル完了条件として 1 行加える。

補助として、**新規ファイルにだけ**粗い閾値（docstring 比率が 45% を超えたら警告）を掛ける案もある。既存ファイルを対象にしないので誤検出のコストが小さい。

## N. 指摘 B-2: 3-C が Goudarzi の対照を再現していない

**エージェント運用ではなく、記事の主張そのものに関わる。**

### 観測

`results/03_capacity/fig_narma10_control.png` は FIG-1/2/3/5/6 をすべて満たしており、図としての完成度は高い。結果は以下。

| 水準 | NMSE |
|---|---|
| 線形 | 1.0181 |
| 遅延線（リッジ） | 0.1538 |
| **遅延線（OLS）** | **0.1534** |
| ESN | 0.2673 |

副題は「**Goudarzi et al. 2014 の対照 (正則化なし) を第4水準に足した**」、タイトルは「遅延線が ESN を下回るのは正則化のおかげではない」。

ところが実測すると、**この設定では過学習が起こりえない**。

- `experiments/03_capacity/config.yaml:142`: `n_lags_grid: [10, 15, 20, 25, 30]`
- 図の footnote: `n_train = 3800`
- タップ数 / 訓練長 = 最大でも **30 / 3800 ≒ 0.008**

`docs/rc-basics-survey.md` が記録している Goudarzi の設定は **1,810〜2,000 タップ / 訓練 2,000 点**、つまり **k / n ≈ 1** である。彼らの対照の本質は「正則化なし」ではなく「**正則化なし かつ k ≈ n_train**」だった。

### 診断

「OLS ≒ リッジ」は実測として正しい。しかし k/n ≈ 0.008 の領域では OLS が壊れる理由が無いので、**この結果は先行の対照設計への批判を検証していない**。副題が「Goudarzi の対照を足した」と書いている分、読者は検証されたと受け取る。

`docs/rc-basics-survey.md` は実験 3-C の位置づけを「先行の対照は正則化なし OLS だった。**公平な対照で再実験する**」に方向転換したが、公平化されたのは正則化の軸だけで、**タップ数の軸が動いていない**。

### 対応

- **(a) 記事の芯を成立させる**: `n_lags` を k/n_train が 1 に近づくところまで掃引し、OLS が壊れてリッジが壊れない点（あるいは両方壊れる点）を示す。survey の未解決事項3「Goudarzi の DL をリッジ化した追試は誰かやっているか」とそのまま接続する
- **(b) 射程を限定する**: 掃引しないなら、副題と注から「Goudarzi の対照」の主張を外し、「小さいタップ数では正則化の有無が結論を変えない」という限定された主張に書き換える

どちらでもよいが、**現状の副題のままにするのは避けること**。

## U. この 3 巡で見えた一般則

3 度の測定を通して、同じ形が繰り返し出た。記録しておく価値がある。

**対策を置いた層が、そのまま次に破れる場所になる。**

| 巡 | 機械層に落としたもの | 結果 | 同じ巡で手続き層 / プロンプト層に残したもの | 結果 |
|---|---|---|---|---|
| 1 巡目 | 成果物のバイト不変（D-74）、hook の処理系（D-73） | 機能した | docstring 規約（`CLAUDE.md` のみ） | 新規コードが規約前と同比率で書かれた |
| 2 巡目 | 行数ラチェット（D-77）、図の方針（`test_figure_policy.py`） | 機能した | `reviewer-deletion` の実行（完了条件に記載） | **実行されず、重複が 4 件増えた** |

振り返り 4 節は「効いたのは機械層、効かなかったのはプロンプト層」と結論した。この 3 巡が追加するのは、**手続き層はプロンプト層と同じ側に落ちる**という点である。「やること」として文書に書いただけの手順は、**やらなかったことに気づく機械が無ければ、やらない回が出る**。

したがって是正の設計原則は 1 つに縮む。

> **対策を手続きとして書いたら、その手続きが実行されたかどうかを機械で見られる形にセットで作る。**
> それができないなら、手続きではなく機械そのものに落とし直す。

行数ラチェットが成功したのは、それが「割る手順」ではなく「割らないと落ちる機械」だったからである。同名重複も同じ形に落とせる（B-1）。
