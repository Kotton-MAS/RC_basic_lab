## 1. 設計判断の記録がコードに常駐している（最大の原因）

docstring が 32% あるだけでなく、その中身が**「なぜそうしたか」「以前はこうだった」「代案を採らなかった理由」**になっている。

### 実例

`experiment/capacity_pipeline.py::SectionTiming` の docstring は 20 行あり、その大半が

- 3-C だけ `wall_time_s` の意味が違う理由
- フィールドを足す代案（`wall_time_scope` 等）を採らなかった理由
- そう判断した根拠の実測値

で占められている。

### 問題は「3箇所に同じことが書いてある」こと

| # | 場所 | 検査 |
|---|---|---|
| 1 | `.claude/decisions.yaml`（`rule` + `rationale`、53 件） | `check_decisions.py` がスキーマのみ検査 |
| 2 | `docs/design.md`（1,687 行） | `test_design_doc.py`（1,231 行）が機械照合 |
| 3 | `src/**/*.py` の docstring（約 6,000 行） | **無検査** |

`.claude/decisions.yaml` の冒頭には「**正本は散文ではなくこのファイル。背景説明は `docs/design.md` を参照**」と自分で書いてある。つまり運用ルール上、コードに rationale を書く必要はもう無いのに、書かれ続けている。

3 箇所あると 3 箇所が独立にドリフトする。`docs/process/agent-operations-retrospective.md` 2.5 節の 2 件（`stability.py` と `freerun.py` の docstring が実装と逆のことを書いていた）はこのドリフトの実例であり、うち 1 件は成果物 320 行中 240 行の数値誤りにつながっている。

### 対応

docstring は **「何を返すか・前提・送出する例外」に限定する**。「なぜ / 以前は / 代案 / 実測の経緯」は `.claude/decisions.yaml` か `docs/adr/` に移し、コード側は `(D-37)` の 1 トークン参照だけ残す。

> 効果の見積り: `src/` が 2,000〜3,000 行縮む。振る舞いは 1 行も変わらないので、**リスクが最も低く効果が最も大きい**。

## 2. 実験4本ぶんの同じ骨格が4回書かれている

| 重複 | 箇所 |
|---|---|
| `_sweep()` | `capacity.py:992` と `esp.py:712` に別実装（docstring に「02 の `_sweep`」と自認あり） |
| `capacity_context()` | `capacity.py:580` と `stability.py:340` に 2 つ |
| `SectionTiming` | `capacity_pipeline.py:97` と `freerun_pipeline.py:105` に 2 つ（フィールドが別物） |
| `_new_figure` / `_save` | plotting 4 モジュールに各 4 コピー |
| `write_*_csv`（`csv.DictWriter`） | 11 箇所 |
| `to_summary()` | 13 箇所、中身はほぼ `dataclasses.asdict(self)` |
| `if not rows: raise ValueError("rows が空です")` | 13 箇所 |
| `with matplotlib.rc_context(rc_params_for(style)):  # type: ignore[arg-type]` | 17 箇所 |

最後の行が象徴的である。`# type: ignore` 16 箇所は `CLAUDE.md` の「理由なく使わない」に実質抵触しているが、**本質的には 1 箇所で済む**ものが 17 回コピーされているだけである。

### 対応（優先順）

1. **`plotting/_canvas.py` に `figure_context(style, width, height)` を 1 つ作る。** `rc_context` + `_new_figure` + `_save` + 空チェック + `type: ignore` を全部封じる。17 箇所 → 1 箇所
2. **`experiment/_sweep.py` に汎用スイープを 1 本。** 条件生成とログ整形は callable で渡す
3. **`experiment/_csv.py` に `write_rows(rows, columns, path)` を 1 本。** `write_*_csv` 11 本は薄いラッパになる
4. **`to_summary` を Protocol か mixin 1 つに寄せる**

## 3. 行の dataclass が巨大でフラット

| クラス | フィールド数 | 行数 |
|---|---|---|
| `FreeRunRow` | 40 | 78 |
| `CapacityRow` | 39 | 52 |
| `EspRow` | 27 | 36 |
| `StabilityRow` | 20 | 44 |
| `ResultRow` | 17 | 20 |

CSV の列と 1 対 1 なので必然の面はあるが、40 個が平坦に並んでいると**どこまでが条件でどこからが結果か**が読み手に分からない。さらに CSV 列定数（`FREERUN_CSV_COLUMNS` 等）とクラス定義が二重管理になっている。

### 対応

`条件（rho, leak_rate, sigma_u, replicate, seed）` / `結果` / `計測時間` の 3 つにネストし、CSV 化のときだけ prefix 付きで平坦化する。二重管理も同時に消える。

**ただし成果物の列に影響するので着手は最後**。バイト不変検査が通らなくなる唯一の項目である。

## 4. `experiment/__init__.py` が 338 行の手書き再エクスポート

159 本の import 行。実質これが公開 API だが、手書きなので追加漏れが起きる。それを `tests/test_public_api_reexport.py` が守っている＝**コストが表に出ている状態**である。

### 対応

実験層の公開面を「`run_and_report_*` 4 本 + Config 4 種」まで絞る。現状は内部ヘルパまで全部出ており、境界としての意味を持っていない。

## 5. テストについて

20,254 行は実コードの約 2 倍。比率自体は健全だが、内訳に構造的な連動がある。

| ファイル | 行数 | 照合対象 |
|---|---|---|
| `test_diagnostics_ipc.py` | 1,297 | — |
| `test_design_doc.py` | 1,231 | `docs/design.md`（1,687 行） |
| `test_experiment_freerun.py` | 1,031 | — |

`test_design_doc.py` が 1,231 行あるのは design.md とコードを機械照合しているためである。ドキュメントを一次資料にする設計自体は正しいが、**design.md が肥大するほどテストも肥大する**構造なので、第 1 項の整理と design.md の整理はセットで行う。

## 6. 着手順

| # | 内容 | リスク | 効果 |
|---|---|---|---|
| **0** | **成果物（CSV / PNG）の不変を 1 コマンドで言えるゴールデンテストを追加** | — | 以降の全ステップの前提 |
| 1 | `plotting/_canvas.py` 抽出 | 低（plotting 層で閉じる） | `type: ignore` 16 箇所が消える。目に見える |
| 2 | docstring の「なぜ」を `decisions.yaml` / `adr` へ退避 | 低（振る舞い不変） | 2,000〜3,000 行減 |
| 3 | `write_rows` / `to_summary` の共通化 | 低 | 11 + 13 箇所が縮む |
| 4 | `_sweep` / `capacity_context` / `SectionTiming` の統合 | 中（実験層をまたぐ） | 実験 5 本目を足すコストが下がる |
| 5 | `Row` dataclass のネスト化 | 高（CSV 列に影響） | 二重管理の解消 |

### ステップ 0 を必ず先にやる

現状は行の値を検証するテストが厚い一方で、「リファクタ前後で成果物が 1 バイトも変わらない」を一発で言える仕掛けが見当たらない。それが無いまま 2〜4 を進めると、テストの修正とリファクタの区別がつかなくなる。

なお `docs/process/agent-operations-retrospective.md` 4 節は「成果物のバイト不変検査（複合ハッシュ）」を**効いた対策**として挙げている。既にある道具なので、これをリファクタリングの合否判定にそのまま転用できる。

## 7. 触らないほうがよい部分

`config/_common.py` の `load_config_as[T]` は、4 つの config を 1 つの汎用ローダで扱えており重複がゼロである。設計としてはここが一番きれいで、実験層が本来目指すべき形（**共通の骨格 + 実験ごとの差分だけ**）を既に実現している。

今の実験層は、その差分が骨格ごとコピーされている状態、というのが本稿全体の要約になる。

---

## 8. `CLAUDE.md` に足すべき規約

このリファクタリングを一度やっても、規約が無ければ次のサイクルで同じことが起きる。最低限、以下を「コード規約」に追加する（現状は 3 行しかない）。

- モジュールの行数上限（目安 600 行。超えたら分割を検討）
- docstring に書いてよいもの / いけないもの（第 1 項の規律）
- 実験を 1 本追加するときに新規作成してよいファイルと、共通層に足すべきもの
