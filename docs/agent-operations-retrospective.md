## 2. 問題の分類 — 「誰が悪いか」ではなく「どの層に置いたか」

以下、見つかった問題を層で整理する。層は「プロンプト層」（CLAUDE.md やエージェント定義の文言による指示）、
「手続き層」（人・エージェントが実行するチェックリストや運用手順）、「機械層」（フック・スキーマ・テストなど
自動で強制されるもの）の3つ。

### 2.1 フックの検出漏れが自動コミットに焼き付いた（5 回、プロンプト層の失敗）

- `block-mutations.sh` は Edit / Write ツール経由の書き込みは見るが、`sed -i` や python の heredoc
  経由のファイル書き換えを検出しない
- 結果、変異注入のためにコードを一時的に壊した状態で subagent が終了すると、SubagentStop の
  `auto-commit.sh` がその**壊れたコードを wip コミットした**
- 5 回とも、検出したのはテストではなくオーケストレータが `git log` を見て気づいたことによる
- 「変異を戻し忘れるな」という指示（プロンプト層）は 5 回とも守られなかった。
  対策は機械層（`block-mutations.sh` の検出範囲拡張、または `auto-commit.sh` 側での残留変異検査）に
  置く必要がある（→ 提言 3）

### 2.2 層どうしの矛盾 — findings のファイル受け渡し

- CLAUDE.md の規律: 「reviewer の findings は**ファイル経由で fixer に渡す**。プロンプトへの転記は禁止」
  （転記が無ければ渡し漏れは原理的に起きない、という設計）
- 一方 `block-mutations.sh` は read-only agent（reviewer 系）の `mkdir` / `tee` / `cp` を止める設計になっている
- 結果、reviewer は findings JSON を**ファイルに書けない**。48 件の readonly-agent-mutation の相当数はこれが原因
- 実際に取った回避策: reviewer に最終メッセージで JSON を返させ、オーケストレータが保存する運用に変更
- サイクル 04 での改善: subagent の JSONL トランスクリプトから JSON を**機械抽出**する方式に変更。
  人手の転記が一切入らないため、「転記ミスを原理的に無くす」という規律の意図はこの形でも満たされている

### 2.3 空虚なガード 13 件 — 「テストは通るのに、何も守っていない」

**全 13 件が変異注入（実装を意図的に壊してテストが落ちるか確認する手続き）でのみ発見された。**
通常のレビューやテスト実行では見つからなかった。

| サイクル | 対象 | 空虚だった層 | 症状 |
|---|---|---|---|

| 3a | finding ID の解決 | 文書参照 | 存在確認だけで、別サイクルの同番号と衝突しても通る |

| 3a | MC の保存則 | 下限の欠落 | 上限だけを検査し下限は `> 0.0` のみ。容量を 0.02 倍に潰しても通る |

### 2.4 `decisions.yaml` の rationale が唯一の非検査領域（04 で 2 件）

このプロジェクトは「数値は必ず一次資料と機械照合する」という規律を持ち、`design.md` は
`test_design_doc.py`、`README.md` は `test_readme_summary.py` がそれぞれ機械照合している。
ところが `.claude/decisions.yaml` の rationale（散文部分）だけが機械照合の外にある。
`check_decisions.py` はスキーマ（guard_test の実在・id の重複）しか見ない。

04 で見つかった実例:

- D-41: 「ESN が遅延線を**37 倍**上回り」という記述が、一次資料（`design.md:1390`、
  `docs/plans/rc-basics-04.md:809`）ではどちらも**25 倍**。実測値から計算しても
  5.4e-2 / 2.2e-3 = **24.55 倍**であり、37 倍という数値の根拠がない
- D-45: 対照の自己相関ピークは「**0.72 以下**」と記述されているが、`freerun.csv` の実測は
  **0.7167〜0.7602**で、上限を超える値が実測に含まれる

皮肉なのは、「正本は散文ではなく `decisions.yaml`」と位置づけた場所こそが、
プロジェクト内で唯一検査されていない場所だったという点である（→ 提言 1）。

### 2.5 docstring が実装と逆のことを書く（04 で 2 件）

- `stability.py`: 「**真の軌道は条件ごとに積分し直さない**（仕様 §5 禁止する構造3）」と明言しているが、
  実測すると 4 条件で `generate_lorenz` を 4 回呼んでいる（実体は 2 本のはずが、本番 320 条件では
  実体 5 本に対し 320 回積分している計算になる）
- `freerun.py:691`: 「自走のノイズは reservoir ストリームの**続き**」とコメントされているが、
  実装は同じシードから Generator を**作り直して**おり、ノイズは `W_in` / `W` と同じビット位置から
  引かれている。既存の 2 実装（`runner.py:169`、`esp.py:413`）は Generator オブジェクトをそのまま
  渡しており、04 だけがこの点で外れていた

どちらも「守っているつもり」で書かれ、**誰も検査していなかった**。禁止構造を仕様に書き、
docstring で「守っている」と宣言し、それを裏付けるテストが無い、という三点セットが共通点である
（→ 提言 2）。

### 2.6 確保軸のガード — 同じ症状に見える2つの別の失敗（合計6回再発）

確保軸（メモリ・条件数などの上限）の検査は、このプロジェクトで最も再発回数の多い問題であり、
かつ「1〜5回目」と「6回目」で失敗の仕方が違うという、本稿でもっとも重要な発見を含む。

**1〜5回目 (F): 新しい経路が検査を通らない**

- 確保軸の検査を、新しい経路ができるたびに個別に足すという実装を5回繰り返し、
  そのたびに「新しい経路が検査を通らない」という同じ形の再発が起きた
- 3a で方針転換し、**単一の検証済み入口**（`simulate_condition_trajectory`）に処理を集約することで収束した
- ただし 3-C で `run_narma10` がその入口を通っておらず再発。`Narma10Config(length=10**12)` が
  そのまま受理されてしまい、fixer が `_MAX_LENGTH` を追加して対処した
- さらにオーケストレータ自身が `n_units` の穴を発見した。ESN が 6000 ユニットで構築され、
  **14.58 秒後に無関係な shape エラー**で落ちるという遠回りな壊れ方をしていた。
  `validate_n_units_bound` を確保前に置くことで、**5.0 マイクロ秒・ESN 構築 0 回**で落ちるよう修正した

**6回目 (F-2): 検査は通っているが、確保量を決める因子を網羅していない**

サイクル04のセキュリティレビューで、同じ症状（「ガードがあるのに予算を超えた」）が
6回目として再発した。しかし原因は F とは別物だった。

- 実測: 確保軸 8 本の検査を**すべて通過したまま**、peak RSS 5.11 GB（予算 4 GB）に達した。
  再現条件は `lorenz.length=100000` と `base.ridge.n_lags_grid=(1000,)` で、
  どちらも 04 の実 config（`experiments/04_chaotic_freerun/config.yaml`）にある運用ノブである。
  軸1 = 505,005 ≦ 2e7 で通過、軸2 = 300,000 ≦ 5e7 で通過していた。
  さらに大きい合法値（`length=200,000` / `n_lags=60,000`、3軸すべて上限内）では、
  `run_free_run` がプロセスごと **SIGKILL (exit 137)** で落ち、`ValueError` は1つも出なかった
- 原因: 遅延線の設計行列は `(lorenz.length, n_lags * D_in + 1)` の形で確保されるが、
  **この積を縛る軸が表に無い**。軸2は `length * 3`（状態次元）しか見ておらず、`n_lags` が掛かっていない
- 同種のものが他に3本見つかった: `base.n_replicates`（4-Bの自走本数、無検査）、
  chamfer 距離の右側点集合（`_POINT_CHUNK` が抑えるのは左側だけで、`|right|=80,000` で
  peak RSS 8.6 GB）、軸4×軸5の積（1,984条件 × 1e6ステップ ≒ 約13時間、予算300秒。
  両方の単独検査は通過していた）
- さらに `integrate_lorenz` では、**検査している量と確保する量が5桁ずれていた**
  （検査は `cfg.length * 3` = 300、確保は引数 `n_samples * 3` = 3e8 要素）

**F と F-2 の違い**

外から見ると同じ症状（「ガードがあるのに予算を超えた」）だが、失敗の仕方が違うため効く対策も違う。

| | 失敗の仕方 | 効く対策 |
|---|---|---|
| F（1〜5回目） | 新しい経路が**検査を通らない** | 単一の検証済み入口に集約する |
| F-2（6回目） | 検査は**通っているが、確保量を決める因子を網羅していない** | 検査点を**確保点の直前**に置き、確保する量そのものを検査する |

F の対策（単一入口への集約）は F-2 には**効かない**。入口を一本化していても、
検査式に `n_lags` が入っていなければそのまま素通りする。同様に `integrate_lorenz` の例は
「検査点と確保点がずれている」形の失敗であり、これも入口の一本化では直らない。

**症状で対策を選ぶと外す。** 5回連続した F を潰した対策（単一入口への集約）が正しかったからこそ、
6回目もその対策の延長で足りると考えてしまう。実際には別の失敗だった。再発回数を数えるときは、
表面的な症状ではなく**失敗の仕方**で数える必要がある（→ 提言 5）。

### 2.7 fixer が findings 外の関数を追加した（2回）

## 3. オーケストレータ自身のミス

エージェント側の問題だけを並べるのは事実に反するため、正直に記録する。

1. **finding ID の誤引用**: `F-1-011` と `F-1-010` を取り違えて fixer に渡した。
   fixer が `triage.json` を読んで訂正した。これはファイル経由で findings を渡す規律
   （2.2節）がミスの実害を止めた例でもある
2. **決定 ID の衝突（BLOCKER）**: 承認済みの plan doc が D-29〜D-32 を 3b 用に予約していたのを
   確認せず、fixer へのプロンプトで D-29 を採番してしまった。D-33 へ振り直して解消した
3. **base-ref の取り違え**: サイクル 2a の差分を誤った基準 ref から取ってしまった。
   以降、各サイクル開始**前**に base-ref を記録する運用に変更した
4. **変異注入の失敗3回（同一セッション内）**:
   (a) import を1行目に挿入してモジュール docstring を壊してしまった、
   (b) `block_width(n)` → `solve_width(n)` という変異が意味的に no-op だった、
   (c) `solve_width(256)` が小さいテスト設定では幅を変えなかった。
   正しい変異は `solve_width(1)` で、これで初めて3テストが落ちた
5. **ハッシュコマンドの取り違え（4サイクル継続）**: オーケストレータが `shasum`（SHA-1）を使い、
   implementer は `shasum -a 256` を使っていたため、複合ハッシュが「再現しない」と
   4サイクルにわたり誤認し続けた。ただし両者とも `results/` が不変であること自体には合意していた
   （＝実害は無かったが、ツールの不一致に気づくまでに4サイクルかかった）

## 4. 効いた対策と効かなかった対策

### 効かなかった（プロンプト層に置いた対策）

- 「タスクごとにコミット」を CLAUDE.md に明記 → **15回中0回**守られた（本プロジェクト以前からの既知の実測）。
  `auto-commit.sh`（SubagentStop フック）へ層を下げて解決した
- 「変異を戻してから終了せよ」→ 5回とも守られなかった（2.1節）
- reviewer への「evidence は実測で」という指示 → 12件の降格が発生し続けている。
  ただし**降格の仕組みそのものは機能している**ので、プロンプト層の失敗を機械層が受け止めている形になっている

### 効いた（機械層に置いた対策）

- `decisions.yaml` の guard_test 必須 + `check_decisions.py` によるスキーマ検証（53件が維持されている）
- `triage_findings.py` の evidence 検証（裏付けの無い実測主張を12回降格）
- 単一の検証済み入口（確保軸ガードの再発が1〜5回目のパターンでは止まった）
- 成果物のバイト不変検査（複合ハッシュ）。01/02/03 の成果物が04の作業で動いていないことを毎回確認できた
- **変異注入を手続きとして固定したこと**。13件の空虚なガードはすべてこれで見つかった

一貫した傾向として、「〜するな」というプロンプト層の指示は再発を止められず、
検査・フック・手続きという機械層・手続き層の対策だけが再発を止めている。
