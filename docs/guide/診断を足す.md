# 診断を 1 本足す手順

**所要: 1 ファイル + テスト 1 本。既存の CSV は 1 列も動きません。**

`docs/guide/リザバーを足す.md` と同じ形です。違いは、リザバーが「union に足して
`case` を書く」のに対し、診断は**書いた瞬間に契約検査へ載る**（`pkgutil` が
`diagnostics/` を列挙するため、登録作業がありません）。

## 満たすべき署名

```python
def my_diagnostic(X, u=None, y=None, *, ctx, cfg=DEFAULT) -> DiagnosticResult: ...
```

`DiagnosticResult` に入れるもの:

| フィールド | 何を入れるか |
|---|---|
| `name` | 診断名。`diagnostics.csv` の `diagnostic` 列になる |
| `scalars` | `Mapping[str, float]`。**1 キー = 1 行**として長形式へ出る |
| `arrays` | 配列。**CSV には出さない**（行数が爆発するため） |
| `params` | 設定値。文字列で持つ |

`diagnostics/` は **`reservoir` を import しません**。引数は状態行列 `X` で
あってモデルではないので、外部素子由来の状態にもそのまま当たります。

## 結合そのものを測りたいときは、別の族です

次数分布やスペクトルは状態系列 `X` ではなく**結合行列 `W`** の関数です。
これらは `diagnostics/topology.py` に置き、第 1 引数を `W` にします（D-122）:

```python
def my_graph_diagnostic(W, *, ctx=None, cfg=DEFAULT) -> DiagnosticResult: ...
```

**`X` を受け取って無視する診断を書いてはいけません。** 無視してよい引数がある
という前例ができると、D-01 の契約検査そのものが意味を失います。

2 つの族は `pkgutil` 列挙のときに**第 1 引数の名前**で分かれます。除外リストは
無いので、`W` と書けば自動的にトポロジ族へ入ります（`X` と書くと D-01 族へ
落ち、契約検査が赤くなって気づけます）。

モデルから行列を取り出すのは `reservoir.registry.require_graph` の仕事です:

```python
matrix = require_graph(reservoir, used_by="3-T トポロジ掃引")
result = degree_distribution(matrix)
```

`isinstance(res, GraphReservoir)` で分岐しないでください —— 行列を持たない
モデルを渡したときに「トポロジ診断の行だけが静かに消えた成果物」ができます。
`require_graph` は落ちます。

| 実装済み | 何を返すか |
|---|---|
| `degree_distribution` | 次数の最大 / 標準偏差 / 密度 / 裾のべき指数 |
| `spectral_profile` | スペクトル半径 / ギャップ / 固有値の絶対値の分散 |
| `small_world` | クラスタ係数 / 平均最短路長 / 到達率 / sigma |

`networkx` は**テストのオラクル専用**で dev グループにあります。本体は numpy と
`scipy.sparse.csgraph` だけで書きます（実行時依存を増やさない）。

## 出口 — ここが 2026-08-31 に変わりました

以前はスカラを 1 個 CSV に出すのに、行 dataclass にフィールドを足し、
`CSV_COLUMNS` に列を足し、`docs/design.md` の表を直し、成果物を再生成して
指紋とゴールデンを取り直す必要がありました。`CapacityRow` は 39 列あり、
**指数を 1 つ測るたびにこの表が 40 列になる**状態でした。

いまは `results/<exp>/diagnostics.csv` へ**長形式**で出ます（D-118）:

```
experiment,condition_id,replicate,diagnostic,key,value
3A_mc_sweep,leak_rate=0.3|n_units=200|rho=0.5|state_noise=0,0,memory_capacity,mc_total,10.60
```

`DiagnosticResult.scalars` が `Mapping[str, float]` なので**変換なしでそのまま
流れます**。新しい診断を足しても既存 CSV の列が 1 つも動かないので、
指紋も golden も動きません。

**実測（2026-08-31）**: 03 に長形式の出口を足したとき、
`capacity.csv` / `capacity_profile.csv` / `narma10.csv` / `narma10_taps.csv` と
図 5 枚は**バイト一致**のままで、増えたのは `diagnostics.csv` 1 枚だけでした。

### 6 列は増やしません

`experiment / condition_id / replicate / diagnostic / key / value` の 6 列で
固定です。増やせる形にした瞬間に、この層を作った理由（主表の列が診断のたびに
増える）がここで再発します。診断固有の情報は `condition_id` と `key` に入れます。

### `condition_id` の作り方

`experiment/diagnostics_rows.py` の `condition_key` が**唯一の形式**です
（D-118）。振った軸だけを**軸名の昇順**で `name=value` と並べ、`|` で区切ります。

昇順に固定するのは、呼び出し側が dict を作る順に依存させないためです。
順が変わると同じ条件が別のキーになり、実験をまたいだ突き合わせ（03 の容量と
04 の容量を `merge` する）が静かに壊れます。**この形式を後から変えると全実験の
CSV が動く**ので、決定として記録してあります。

## 手順

1. `diagnostics/<name>.py` に関数を書く（`DiagnosticResult` を返す）
2. `tests/test_<name>.py`。**変異注入で赤くなることを確認する**
3. 実験から呼ぶ。結果を `scalar_rows(...)` に渡せば `diagnostics.csv` に出る

`diagnostics/` に置いた時点で契約検査（署名・`reservoir` を import しない・
純関数であること）が自動で載ります。**登録の書き忘れという失敗モードがありません。**

## まだ配線されていない実験

`diagnostics.csv` が出るのは **03 だけ**です。02 / 04 / 05 は同じ形で
`write_diagnostics_csv(...)` を 1 行足せば出せますが、まだ足していません。
足すときは成果物が 1 枚増えるので、指紋とゴールデンの取り直しが要ります。

## やってはいけないこと

- **`arrays` を CSV に出さない。** 行数が爆発します（`capacity_profile.csv` は
  すでに 21,812 行あり、これは正値セルだけに絞った結果です）
- **主表に列を足さない。** 足せるとこの層の意味が消えます
- **`condition_id` の形式を変えない。** 全実験の CSV が動きます
