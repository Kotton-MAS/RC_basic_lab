# RC_basic_lab を「連載用」から「RC 実験基盤」へ広げるための方針

作成日: 2026-08-31
対象: `RC_basic_lab` @ `1b297ce`
想定する今後: **RC モデルを増やす / ベンチマーク課題を増やす / 内部状態を調べる /
スケールフリーなどネットワーク構造の解析**

---

## 0. 先に、すでに解けている問題

同じことを二度やらないために、現状の棚卸しから。実測で確かめた範囲では、
**拡張性の設計としてすでに正解に到達している層が3つ**ある。

| 層 | 状態 | 根拠 |
|---|---|---|
| `reservoir/` | **完成している** | `Reservoir` Protocol（5面）+ 判別子つき union + `build_reservoir` の1本化。4つ目のモデルを足す実測が「3ファイル・`experiment` 層 0 行」 |
| `diagnostics/` | **完成している** | `reservoir` を import しない。全診断が `f(X, u, y, *, ctx, cfg)` の1署名。`pkgutil` 列挙の契約テストがあるので、新しい診断は書いた瞬間に契約検査に載る |
| `config/` | **ほぼ完成** | 実験ごとに独立、未知キーは `ConfigError`、`--set` / `--preset`、`kind` の変化でセクション置換 |

`docs/リザバーを足す.md` は**そのまま他の層のひな型として使える品質**です。
以下の提案は、基本的に「この文書と同じ形を、まだそうなっていない3箇所へ移す」
という話に尽きます。

工程側（成果物のバイト不変・`FROZEN` のラチェット・`decisions.yaml` の
guard_test・`make ci`）も、この規模の個人リポジトリとしてはかなり強い。
**そこは崩さない前提**で書きます。

## 1. 診断結果の出口 —— いちばん効くのはここ **[最優先]**

### 症状

新しい診断を1つ足したときのコストが、**診断本体ではなく出口側**に集中している。

`diagnostics/` に関数を書くのは安い（Protocol が1つ、契約テストは自動で載る）。
高いのはその後で、スカラーを1個 CSV に出すのに:

1. `experiment/<exp>_rows.py` の行 dataclass にフィールドを足す
2. `XXX_CSV_COLUMNS` に列を足す
3. `docs/design.md` の表を直す
4. 成果物を再生成して `make artifacts-manifest`
5. `tests/golden/` の基準を取り直す

`CapacityRow` は現在 **39 列**あり、そのうち診断由来のスカラーが 20 列ほど。
**次数分布の指数を1つ測るたびに、この 39 列の表が 40 列になる。**
列が増えれば既存の指紋も golden も動くので、
「バイト不変が合否判定」という一番強い規律のコストが、
診断を足すたびに払われることになります。

### 手当て

**主表は固定列のまま据え置き、診断のスカラーは長形式の別ファイルへ逃がす。**

`capacity_profile.csv`（すでに長形式）が持っている形をそのまま一般化します。

```
results/<exp>/diagnostics.csv
experiment,condition_id,replicate,diagnostic,key,value
3A_mc_sweep,rho=0.9|leak=1.0,0,memory_capacity,mc_total,20.12
3A_mc_sweep,rho=0.9|leak=1.0,0,memory_capacity,mc_effective_delay,49.62
3A_mc_sweep,rho=0.9|leak=1.0,0,topology_degree,gamma,2.31
```

`DiagnosticResult.scalars` が `Mapping[str, float]` なので、
**変換なしでそのまま流せます**。書き出しは1本の共通関数になる。

得られるもの:

- 新しい診断を足しても**既存 CSV の列が1つも動かない** → 指紋も golden も動かない
- 条件キー（`condition_id`）が実験をまたいで同じ形になるので、
  「03 の容量」と「04 の容量」を後から突き合わせるのが `pandas.merge` 1行になる
  （いまは #4 の 3.6 でやったような手作業）
- `experiment/*_rows.py`（合計 1,082 行）の増加が止まる

やること:

1. `experiment/diagnostics_rows.py` に `DiagnosticScalarRow` と書き出し関数
2. 各実験の pipeline に `write_diagnostics_csv(...)` を1行追加
3. `<EXP>_ARTIFACTS` に `diagnostics.csv` を足す
4. **既存の固定列 CSV は1列も動かさない**（記事が参照しているので）

条件キーの作り方だけ決めておくこと。`rho=0.9|leak=1.0` のような
「振った軸だけを昇順で連結した文字列」が扱いやすいはずですが、
ここは `decisions.yaml` に1本記録する価値があります
（後から形式を変えると全実験の CSV が動くため）。

## 2. トポロジをモデル本体から分離する **[スケールフリー解析の前提]**

### 症状

**`reservoir/` の外で `W` に触っている箇所は 0 件**（実測）。
`Reservoir` Protocol が意図的に `W` を面に入れていないためで、この判断自体は
正しい（再帰行列を持たないモデルはいくらでもある）。

ところが「スケールフリーネットワークの解析」は、状態 `X` ではなく
**結合行列そのもの**を見る話です。つまり現状のアーキテクチャには
**置き場所が無い**。

もうひとつ。結合構造の生成が各モデルに埋まっています。

```python
# esn.py と deep.py に同じものが2箇所
mask = rng.random((n_units, n_units)) < density
```

`density` は `ESNConfig` と `DeepESNConfig` の両方にフィールドとしてあり、
どちらも Erdős–Rényi 固定。**この形のままスケールフリーを足すと、
「BA トポロジの ESN」という新しいモデルを1つ足すことになります。**
Watts–Strogatz を足せばもう1つ。組み合わせ爆発する側の設計です。

### 手当て（2段構え）

#### 2-1. 生成側: `topology` を独立した軸にする

```python
# reservoir/topology.py （新規）
type TopologyConfig = ErdosRenyiConfig | WattsStrogatzConfig | BarabasiAlbertConfig | RingTopologyConfig

def build_adjacency(config: TopologyConfig, n_units: int,
                    rng: np.random.Generator) -> FloatArray:
    match config:
        case ErdosRenyiConfig():   ...   # 現行の density と同じ挙動
        case BarabasiAlbertConfig(): ...
```

`ESNConfig.density: float = 0.1` を
`ESNConfig.topology: TopologyConfig = ErdosRenyiConfig(density=0.1)` に置き換える。

**既定を `ErdosRenyiConfig(density=0.1)` にすれば既存の乱数の引き方も
バイトも変わりません** —— `rng.random((n,n)) < density` をそのまま移すだけなので。
これは D-74 の合否判定をそのまま通せるリファクタです。

得られるもの:

```yaml
esn_mackey_glass:
  kind: esn
  n_units: 200
  topology:
    kind: barabasi_albert
    m: 2
```

**モデルを1つも足さずに、更新式を固定してトポロジだけを振る実験が
YAML で書けるようになります。** これが「スケールフリーの効果を測る」実験の
最小の形で、しかも `reservoir` と `deep_esn` の両方が同時に対応します
（両者が同じ `build_adjacency` を呼ぶので）。

`ring.py`（SCR）も `RingTopologyConfig` として取り込めるなら、
モデルが1つ減って軸が1つ増える、という良い方向の交換になります。
ただし SCR は入力重みの作り方もランダムでない（大きさ一定・符号だけランダム）ので、
**そこまで一緒に畳もうとしないほうがいい**と思います。トポロジだけ共有して
モデルは残す、が安全側。

#### 2-2. 解析側: `X` を取る診断と `W` を取る診断を分ける

**同じ `Diagnostic` Protocol に混ぜないこと。** 混ぜると
「`X` 引数を無視する診断」が生まれ、`pkgutil` の契約テストが意味を失います。

```python
# reservoir/protocol.py に第2の面を足す（任意実装）
@runtime_checkable
class GraphReservoir(Protocol):
    """結合を明示的な行列として持つモデルだけが満たす面。"""
    def adjacency(self) -> FloatArray: ...

# diagnostics/topology.py （新規・別の署名族）
def degree_distribution(W, *, ctx=None, cfg=DEFAULT_DEGREE) -> DiagnosticResult: ...
def spectral_profile(W, *, ctx=None, cfg=...) -> DiagnosticResult: ...
def small_world(W, *, ctx=None, cfg=...) -> DiagnosticResult: ...
```

`Reservoir` の5面は**広げない**（既存の規律どおり）。
`GraphReservoir` は「持っているモデルだけが満たす追加の面」で、
解析側が `isinstance(res, GraphReservoir)` で分岐するのではなく、
**トポロジ解析の実験だけがこの面を要求する**（`require_esn` と同じ流儀で
`require_graph(res, used_by=...)`）。

依存の向きは `diagnostics/topology.py` も `reservoir` を import しないこと。
引数は `FloatArray` の隣接行列であって `Reservoir` ではない、という形にすれば、
外部素子の結合行列にもそのまま当たります（`diagnostics/` の既存方針と同じ）。

**実行時依存**: `networkx` を入れたくなりますが、規約は「実行時依存を増やさない」。
次数分布・クラスタ係数・平均最短路長・スペクトルギャップくらいなら
`numpy` + `scipy.sparse.csgraph`（`shortest_path` / `connected_components`）で書けます。
**`networkx` は dev グループに入れてテストのオラクルにする**のが今の規律に合います
（D-62 と同じ扱い）。

## 3. 課題をリザバーと同じ扱いにする **[ベンチマーク追加の前提]**

### 症状

`runner.build_tasks` は 2 課題がハードコードで、しかも設定側に
**平行なフィールドが4つ**並んでいます。

```python
class ExperimentConfig:
    mackey_glass: MackeyGlassConfig
    delay_parity: DelayParityConfig
    esn_mackey_glass: ReservoirConfig      # 課題ごとのリザバー設定
    esn_delay_parity: ReservoirConfig
TASK_LENGTH_FIELDS = {"mackey_glass": "mackey_glass", ...}   # さらに写経が1枚
```

課題を1つ足すと触る場所: 設定 dataclass / フィールド2つ / `TASK_LENGTH_FIELDS` /
`build_tasks` / 図 / テスト。**リザバーが3ファイルで済むのと非対称**です。

（フィールド名が `esn_*` のままなのも、`TaskEntry.esn` → `reservoir` の改名を
したときに置いていかれた分だと思います。型はすでに `ReservoirConfig` です。）

### 手当て

`reservoir` と**同じ形**にする。判別子つき union + 生成口1本。

```python
# tasks/protocol.py （新規）
type TaskConfig = MackeyGlassConfig | DelayParityConfig | Narma10Config | ...

# tasks/registry.py （新規）
def build_task(config: TaskConfig, rng) -> TaskData:
    match config:
        case MackeyGlassConfig(): return generate_mackey_glass(config, rng)
        ...
```

そのうえで、**課題ごとのリザバー設定を課題設定の中に入れて、
課題をリストにする**。

```yaml
tasks:
  - kind: mackey_glass
    horizon: 1
    reservoir: { kind: esn, leak_rate: 0.3 }
  - kind: delay_parity
    delay: 1
    reservoir: { kind: esn, leak_rate: 1.0 }
  - kind: narma10                      # ← 足すのはこの3行
    length: 8000
    reservoir: { kind: esn, leak_rate: 1.0 }
```

得られるもの:

- 課題を足す = `tasks/<name>.py` + union に1行 + `case` を1つ + テスト。
  **リザバーとまったく同じ3ファイル**
- `TASK_LENGTH_FIELDS` が消える（`length` は課題設定が持つ）
- `esn_<task>` の平行フィールドが消える
- **03 の NARMA10 が 01 の経路に載る。** いまは `experiment/narma.py`（382 行）が
  `Narma10Config.base` に `ExperimentConfig` を丸ごと内包して `run_task` を
  呼び直しています。課題がリストになれば、NARMA10 は 01 の設定に1エントリ足すだけ
- 将来「ベンチマーク10本を一括で回す」が設定の行数で書ける

**移行の注意**: `ExperimentConfig` の形が変わるので `results/01` の
`meta.json` が動きます。D-74 の判定を通すには、
`meta.json` に出す設定の形を維持する互換層を1枚挟むか、
**意図した変更としてコミットメッセージに理由を書いて指紋を取り直す**か。
後者のほうが正直で、この規模なら後者を勧めます。

## 4. 掃引軸が ESN 固有の名前で書かれている **[モデル追加の残りの壁]**

### 症状

`require_esn` が 03-C / 04 / 05 を ESN に縛っています。理由は文書にも明記のとおり
「掃引軸が `spectral_radius` / `leak_rate` / `state_noise` という ESN 固有の概念だから」。

これは配線ではなく実験設計の問題、という整理はそのとおりです。ただ
**「そのモデルで何を振るか」を YAML で宣言できるようにすれば、配線側は一般化できます。**

### 手当て

面（`Reservoir` の5つ）は広げない。**設定側に2つのメソッドを足す**。

```python
# 各 ReservoirConfig が満たす（dataclass なので実装はほぼ共通）
def sweepable_axes(self) -> frozenset[str]: ...        # {"spectral_radius", "leak_rate", ...}
def with_axis(self, name: str, value: float) -> Self:  # dataclasses.replace の薄い包み
```

掃引側は軸名を**設定から**受け取る:

```yaml
mc_sweep:
  axes:
    spectral_radius: [0.5, 0.7, 0.9, 0.95, 1.0, 1.1]
    leak_rate: [0.3, 0.6, 1.0]
```

モデルが持たない軸を要求したら、`require_esn` と同じ調子で
**「そのモデルにその軸は無い。持っている軸はこれ」**と言って落とす。

得られるもの:

- `ring` なら `{input_scale, n_units}` を、`deep_esn` なら `{n_layers, leak_rate}` を
  振る掃引が、**同じ掃引コードで**書ける
- 2 の `topology` と組み合わせると `topology.m`（BA の枝数）も軸になる
- `require_esn` が消える（呼び出し 3 箇所）

**やらないほうがいいこと**: 軸名をモデル間で共通化しようとしないこと。
`leak_rate` を持たないモデルに `leak_rate` の別名を生やすと、
「同じ名前だが意味が違う軸」ができて、図をまたいだ比較が静かに壊れます。
**軸は各モデルの言葉のまま、集合が違うことを許す**のが正解だと思います。

## 5. 実験を1本足すコスト（構造の話）

### 症状

`experiment/` が **15,000 行 / 40 モジュール**、記事番号での縦割り。
`FROZEN`（600 行超で凍結）7 本のうち **5 本が `experiment/`**。

実験を1本足すと必ずセットで増えるもの:

| 増えるもの | いまの数 |
|---|---|
| `experiments/0N_*/run_0N.py` | 5（各 62〜126 行、中身はほぼ同型） |
| `experiment/<exp>_pipeline.py` + `ARTIFACTS` タプル | 5 |
| `experiment/<exp>_rows.py` | 4 |
| `config/<exp>.py` | 5 |
| `plotting/figures_<exp>.py` | 多数 |
| `Makefile` の `figures-0N` | 5（手書きの長いコメント付き） |
| `main.py` の `EXPERIMENTS` エントリ | 5 |

`run_0N.py` 5 本と `Makefile` 5 ターゲットと `EXPERIMENTS` 5 エントリは
**同じ事実を3箇所に書いている**状態です。

### 手当て

**実験の宣言を1箇所（データ）にする。**

```python
# experiments/03_capacity/spec.py
SPEC = ExperimentSpec(
    name="03_capacity",
    config_type=Capacity03Config,
    variants={
        "main":     run_and_report_capacity,
        "length":   run_and_report_length_sweep,
        "symmetry": run_and_report_symmetry_sweep,
    },
    artifacts=CAPACITY_ARTIFACTS,
    budget_s=900,
)
```

- `main.py` は `experiments/*/spec.py` を列挙する（`EXPERIMENTS` 辞書が消える）
- `Makefile` は `figures-%` のパターンルール 1 本になる
- `run_0N.py` の 5 本が消えるか、1 本の汎用ランチャになる
- `--length-sweep` / `--symmetry-sweep` のような真偽フラグが
  **`--variant length` に統一される**（フラグが1つ増えるたびに
  `parse_args` と `main` の if が両方伸びる形が止まる）

これは急ぎではないですが、**6本目・7本目を足す前にやると効きます**。
逆に言うと、いま足すとしたら「やってから足す」のが安い順序です。

## 6. 名前

パッケージ名が `rc_basics_lab`（連載の基礎編）です。
これから汎用の RC 実験基盤にするなら、**いま考えたほうが安い**。
後で改名すると全 import path と `decisions.yaml` / `design.md` の参照が動きます。

`docs/` も、連載固有のもの（`series/`、`plans/修正指示_*`）と
汎用のもの（`モジュール地図.md` / `リザバーを足す.md` / `条件を変えて試す.md`）が
混ざっています。**汎用側だけを別リポジトリへ持ち出せる形**にしておくと、
「基盤」と「連載」を分ける日が来たときに切れます。

---

## 7. やらないほうがいいこと

- **プラグイン機構（`entry_points` / 動的 import）を入れない。**
  モデル 4 個・課題 6 個・診断 10 個の規模では、判別子つき union +
  mypy の網羅性検査のほうが強い。動的にすると「`case` の書き忘れを型検査が落とす」
  という現在いちばん効いている性質を失います
- **抽象基底クラスに寄せない。** 構造的型付け（Protocol）のまま。
  `diagnostics/` が `reservoir` を知らないでいられるのはこれのおかげです
- **`FROZEN` の数値を上げない。** 上の 1 / 3 / 5 はどれも
  「既存モジュールを太らせずに新しいモジュールへ出す」形になっています
- **`results/01`〜`05` の数値を変えない。** 記事が参照中です。
  2 の topology 分離と 4 の軸一般化は、既定を現行と同じにすれば
  バイト不変で通せます。3 の課題レジストリだけは `meta.json` が動くので、
  そこだけ意図した変更として扱う

## 8. 着手順の提案

| 順 | 項目 | 効くもの | バイト不変で通るか |
|---|---|---|---|
| 1 | **診断の長形式 CSV**（§1） | 内部状態解析すべて。以後の追加コストが一定になる | 通る（既存 CSV は不変、新規ファイルが1枚増える） |
| 2 | **topology の分離**（§2-1） | スケールフリー実験。既存2モデルが同時に対応 | 通る（既定を ER にすれば乱数列も同じ） |
| 3 | **`diagnostics/topology.py`**（§2-2） | 次数分布・スモールワールド性の測定 | 通る（新規） |
| 4 | **課題レジストリ**（§3） | ベンチマーク追加。NARMA10 の特別扱いが消える | `meta.json` が動く（意図した変更として扱う） |
| 5 | **掃引軸の一般化**（§4） | ESN 以外のモデルで 02〜05 が回る | 通る（既定の軸名を現行と同じにすれば） |
| 6 | **実験スペックのデータ化**（§5） | 6本目以降のコスト | 通る |

1〜3 は独立に進められて、どれも既存の成果物に触りません。
**まず 1 と 2 だけやってみて、「スケールフリーの ESN で MC を測る」が
設定だけで書けるところまで到達する**のが、いちばん手応えのある最初の一歩だと思います。
そこまで行けば、以後の解析はほぼ全部「診断を1本書く」で済むようになります。

## 付録: 拡張手順書として足りていないもの

`docs/リザバーを足す.md` が非常に良いので、同じ形で 3 本欲しいところです。

- `docs/課題を足す.md`（§3 のあとに書く）
- `docs/診断を足す.md`（§1 のあとに。`DiagnosticResult` の返し方と長形式 CSV への載り方）
- `docs/実験を足す.md`（§5 のあとに。CLAUDE.md の「実験を1本足すときに触る場所」を昇格させる）

いずれも**実測を書く**のが `リザバーを足す.md` の一番の美点です
（「使い捨ての4つ目を足して 3 ファイルだった」という一文が、
読み手にとっての信頼の全部になっている）。同じことを各手順書でやる価値があります。
