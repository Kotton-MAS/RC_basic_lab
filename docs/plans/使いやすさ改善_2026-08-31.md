# 使いやすさ改善 — 仕様

**目的**: このリポジトリを「記事 01〜05 の再現装置」から
「**RC モデルを足したり調整したりするための土台**」にする。

依頼者の懸念（原文）:

1. README が結論の記載だけで、実際の使い方が無い
2. 手元で条件を変えながら修正する仕組みができていない
3. コードが（依頼者視点で）ちょっと読みにくい

## 実測した現状

### 拡張点

| 事実 | 実測 |
|---|---|
| リザバーの実装 | `reservoir/esn.py` **1 本のみ** |
| `ESN(...)` の直接生成 | **5 箇所**（`runner` / `horizon` / `esp` / `freerun` / `anomaly`） |
| リザバーの抽象 | **無い**。`TaskEntry.esn: ESNConfig` と具体型で受けている |
| 外から使われる ESN の面 | `run` / `step` / `config` / `n_units` / `n_inputs` の **5 つ** |
| 外から使われない公開面 | `W_in` / `W` / `initial_state` の **3 つ**（参照 0） |
| 読み出し形状の分岐 | `_layout_of` の **1 箇所**に正規化済み（ここは良い設計） |

→ **読み出し側（`FeatureSpec`）は既に開いている。閉じているのはリザバー側**である。
モデルを 1 つ足すと 5 箇所を触ることになる。

### 試行環境

| 事実 | 実測 |
|---|---|
| CLI の引数 | `--config` と `--out` だけ（03 のみ掃引フラグあり） |
| 1 つの値を変える手順 | YAML を複製して編集する |
| 既定の出力先 | **`results/`** = バイト不変が保証された成果物 |
| 手元で試したときの副作用 | `tests/artifact_manifest.csv` の指紋と食い違い **`make ci` が赤くなる** |
| 反復にかかる時間 | 03 が約 8 分、05 が約 6 分。**振って確かめられない** |

→ **試行と成果物が同じ場所を奪い合っている。**これが最大の摩擦である。

### README

455 行。全節が「何が分かるか（実測値）」で、結論の記録としては充実している。
一方で「条件を変える」「モデルを足す」導線は無い。

## PR の分割

**この順に 1 本ずつ出す。**後ろの PR は前の PR の成果を前提にする
（試行環境が無いと拡張点を試せず、両方が無いと README に正しいことを書けない）。

### PR-A: リザバーの拡張点を開く

- `reservoir/protocol.py` に `Reservoir` Protocol を置く（`run` / `step` /
  `config` / `n_units` / `n_inputs` の 5 面だけ。**実測で使われている面しか入れない**）
- `reservoir/registry.py` に `build_reservoir(config, rng, n_inputs)` を置き、
  `kind` で分岐する。**既定は `esn`** なので既存 YAML はそのまま通る
- `ESN(...)` の直接生成 5 箇所を `build_reservoir` へ寄せる
- 使われていない公開面 3 つ（`W_in` / `W` / `initial_state`）を落とす
- **合否判定は成果物のバイト不変**（D-74）。既定経路の乱数の引き方を変えない

受け入れ条件: `uv run pytest tests/test_artifact_invariance.py` が緑のまま、
`docs/` に「モデルを 1 つ足す手順」が書けること。

### PR-B: 試行環境

- `--set key.path=value` で YAML を触らず上書きできるようにする（全 run スクリプト共通）
- `--preset quick` で縮小設定を短時間で回す
- **既定の出力先を `results/` から `scratch/` へ移す**。`results/` へ書くのは
  `make figures-0N` の明示的な経路だけにする（`scratch/` は gitignore）
- `--set` は `meta.json` に記録する（何を振ったか成果物から辿れる）

受け入れ条件: `--set` の全キーに「値を変えたら出力が変わる」テストが付くこと（D-13）。
既存の `make figures-0N` の出力がバイト不変であること。

### PR-C: 可読性

依頼者が挙げた 4 症状すべてに対応する。

| 症状 | 対処 |
|---|---|
| 説明の散文が多すぎる | 「なぜ / 以前は / 実測の経緯」を `decisions.yaml` / `docs/adr/` へ寄せ、コードには ID 参照だけ残す（CLAUDE.md の既定の規約。実際には守られていない） |
| モジュールが多く、どこを見ればいいか分からない | `docs/モジュール地図.md`：層ごとに「ここを見る / ここは見なくていい」を書く |
| 層の関係・データの流れが見えない | 一方向依存（`tasks → readout/reservoir → diagnostics → experiment → plotting`）の図を Mermaid で置く |
| 命名や型が追いにくい | `FeatureSpec` など抽象名に実体の対応表を付ける。日英混在の方針を 1 箇所に決める |

**散文の削減は量を測ってから行う。**「読みにくい」は主観なので、
削減前後の行数と、依頼者に読んでもらう対象ファイルを決めてから着手する。

### PR-D: README の書き直し

実測値の節は**残す**（結論の記録としての価値は高い）。上に以下を足す:

- 5 分で動かす（`--preset quick` を使う）
- 条件を変える（`--set` の例）
- モデルを足す（PR-A の手順）
- 層の地図（PR-C の図を参照）

長くなるので、実測値の節は `docs/results/` へ分割することも検討する。

## 全 PR に共通する制約

- **成果物のバイト不変が合否判定である**（D-74）。使いやすさのための変更で
  `results/` の中身を変えない。変える必要が出たら、その時点で相談する
- 実行時依存は増やさない（現在 matplotlib / numpy / pyyaml / scipy の 4 つ）
- 1 モジュール 600 行の上限は緩めない（D-77）
- 新しいコードには必ずテストを書く
