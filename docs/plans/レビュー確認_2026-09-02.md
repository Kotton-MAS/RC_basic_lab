```json
{"kind": "mackey_glass",

 "reservoir": {"kind": "esn", ..., "topology": {"kind": "erdos_renyi", "density": 0.1}}}
```

情報がゼロだった 2 ケースも解消:

| | 前 | 後 |
|---|---|---|
| `ESNConfig(topology=RingTopologyConfig())` | `"topology": {}` | `"topology": {"kind": "ring"}` |
| `RingConfig()` | `kind` なし（`ESNConfig` と field の有無でしか区別できない） | `"kind": "ring"` |

`as_plain_mapping` を経由する形になり、round-trip の guard（D-129）も付きました。
**指摘の要点だった「読み直せる形を作ったのに、永続する記録は読み直せない形で書かれている」が
構造ごと消えています。**

### §3 入れ子の軸 —— 直っています。**指摘より良い形です**

```
ESN + BA の軸: [..., 'topology.m']
ESN + ER の軸: [..., 'topology.density']
Ring    の軸: [...]                      ← topology を持たないので入れ子なし
```

私は「ドット記法を 1 段許す」としか書きませんでしたが、実装は
**軸の集合が `kind` に依存する**形になっています。BA の設定に `topology.density` を要求すると

入れ子の側でも防いでいるということで、こちらのほうが正しい設計です。

境界も宣言どおりでした: `topology.kind` は拒否、`topology.m.x`（2 段）も拒否。

## 残っている小さいもの（どれも急ぎません）

### 1. `kind: "ring"` が 2 つの意味を持つ

```
RingConfig.KIND         = "ring"   # SCR モデル (Rodan & Tino 2011)
RingTopologyConfig.KIND = "ring"   # 巡回トポロジ
```

**動作は正しい**ことを end-to-end で確認しました —— 位置で曖昧さが解けるので、
`reservoir: {kind: ring}` と `reservoir: {kind: esn, topology: {kind: ring}}` は
別物として読み込まれ、`meta.json` にも別物として残ります。

問題は読み手側だけです。アーカイブした `meta.json` を `grep ring` したとき、
この 2 つが混ざります。しかも両者は**近いが同じではない**（SCR は入力重みの大きさも固定する）ので、
混ざると厄介な種類の近さです。片方を `cycle` にするか、`RingTopologyConfig` の docstring に
「`kind: ring` のリザバー（SCR）とは別物。こちらは結合の形だけ」と 1 行あると安全です。

### 2. docstring の「17 本」がシードに依存する

自己ループの表の本数は seed 依存です（guard は seed 7、私の手元 seed 0 では **16 本**）。
guard が固定しているのは**真偽**（自己ループが有る / 無い）だけで、本数ではありません。
このリポジトリの規律だと「テストが見ていない数がプロセに残っている」形なので、
`(seed 7 で 17 本)` と書くか、本数を落として「有り」だけにするのが安全だと思います。

### 3. `presets/scalefree.yaml` が実在しない

`docs/guide/条件を変えて試す.md` が
`# experiments/01_what_is_rc/presets/scalefree.yaml` として例示していますが、
`presets/` にあるのは `deep.yaml` / `quick.yaml` / `ring.yaml` の 3 本です。
例示として読めば足りますが、**置いてしまえば `--preset scalefree` がその場で動きます**。
`deep.yaml` / `ring.yaml` がモデルのプリセットとして在るので、トポロジ側にも 1 本あると対称です。

### 4. `ARTIFACT_RTOL` の rationale がまだ実態と少しずれている

これは前回 §0 に書いたもので、§1〜§5 に番号を振らなかったので手つかずです（当然です）。

docstring は「全列にバイト一致を要求していた版は**開発機以外では通らなかった**」
→ だから許容差を入れた、と読めます。実際に許容差の根拠として記録されているのは
**GitHub Actions の macOS runner と開発機**の差（最大 3.0e-3）で、
私の OpenBLAS では **5.5e-3〜1.8e-2** で通りません。つまり CI を緑に保っているのは
許容差ではなく `test_ci_runs_on_macos_because_the_goldens_are_platform_locked` の
**macOS 固定**のほうです。

`ARTIFACT_RTOL` の docstring は「2 つの実測に挟まれて決まる」と非常に丁寧に書かれているので、
その下限側の表に「**実測範囲は macOS の 2 実装間**であり、他の BLAS では超えることがある
（OpenBLAS で 1.8e-2 を実測）」と 1 行足せば、記録と実態が揃います。
許容差そのものを広げる必要は無いと思います —— 広げると「構造変更を捕まえる」上限側に近づくので。

### 5. `make help` が `uv run python` を起動するようになった

`CATALOG` から生成するのは正しい方向ですが、**環境が壊れているときに `make help` も落ちます**。
`help` は普通そういうときに叩くものなので、`|| echo "  figures-0N  - (CATALOG を読めませんでした)"`
のようなフォールバックが 1 行あると親切かもしれません。
